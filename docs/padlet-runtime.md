# Padlet browser runtime

The 512 MiB Render runner was killed for exceeding its memory limit when it held multiple live Padlet pages. Padlet keeps only one browser context and board page open. Each guest's cookies, local storage and IndexedDB state remain isolated; switching guests closes the entire previous context. Closing only the page retained too much context memory.

Normal runs divide the total equally among guests (the first guests take the remainder) and finish each guest's quota on its existing page before loading the next guest. The first post starts as soon as the first guest is ready. Guests with no assigned posts are not started. For five guests and twenty posts this reduces board loads from 25 (five initial loads plus twenty round-robin reloads) to five. This is a load-count reduction, not a measured fivefold throughput claim. The configured per-guest interval still measures request start to request start; when posting has already consumed that interval, there is no extra timer. Confirmations, access errors, rate-limit stops and the shared total remain enforced. TLK scheduling is unchanged.

Navigation and board readiness each allow up to 90 seconds. Images, media and web fonts are skipped; scripts, styles and API requests are retained. Publication is never automatically retried after an ambiguous result.

Publication confirmation snapshots every `postWrapper` ID immediately before Publish, then looks for a new numeric saved ID with the expected title and body (and the generated guest name when available). Shelf boards keep off-screen wrappers mounted while omitting their contents; the adapter scrolls a new placeholder into view to mount its card. It does not count visible duplicate text or wait for that count to increase. Successful logs include the actual post ID. A reported timeout at 2026-10-15 16:03 UTC corresponded to already-published post 4100450311; its wrapper existed but its body was absent off screen. Fixtures cover lazy mounting, disappearing old duplicate bodies, client-only draft IDs, and unrelated posts. This fixes the confirmation mechanism; it does not establish TLK-equivalent throughput on the free runner.

After Publish, first-time guests may see Padlet's guest-name form while the composer remains open. The adapter waits for either that form or the composer closing, confirms the suggested guest name (uses `Guest` only when empty), then waits for the composer to close and new content to appear. It never clicks Publish twice. Both Korean and English Done labels are covered by delayed-modal fixtures, including a stalled submission and subsequent posts without a modal. A manual `dd`/`dd` post on the reported board reproduced this form and completed after Done; this is separate from a deployed-runner posting test.

For diagnostics, `/api/start` accepts `checkOnly: true` in an otherwise normal Padlet config. It prepares every guest, records readiness and closes all sessions without calling `send`. It uses the normal single-job lock and `/api/stop`. The default is false; non-boolean values are rejected. This checks board access, not successful publication.

Run `node --test test/padlet.test.mjs test/padlet.browser.test.mjs` with `BROWSER_TESTS=1` and an installed Playwright Chromium. The browser tests use intercepted fixtures and never post to Padlet. They check single-page concurrency, guest cookie separation, queue cancellation, slow readiness, essential-resource loading and publication confirmation.
